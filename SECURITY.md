# Архитектура безопасности и аудит ServFlow

> **Комплексный отчёт об архитектуре безопасности, устранённых уязвимостях (K1–K7, B1–B10), политике защиты персональных данных и лицензиях используемых компонентов.**

---

## 1. Архитектурные принципы безопасности

Система «КофеСервис Регион / ServFlow» спроектирована по концепции **Zero Trust (нулевое доверие)** и многоэшелонированной защиты (Defense-in-Depth):

1. **Принцип наименьших привилегий (Least Privilege):** Каждый пользователь имеет строгую ролевую модель (`dispatcher`, `engineer`, `company`). Все закрытые маршруты защищены зависимостями FastAPI (`require_roles`, `require_dispatcher`).
2. **Изоляция арендаторов (Tenant Isolation / Anti-IDOR):** Пользователи компаний (`role="company"`) получают доступ строго к данным своей организации (`company_id`). Попытки обращения к чужим веткам обращений, технике или заказам блокируются на уровне SQL-фильтрации.
3. **Безопасная обработка входа и защита от Prompt Injection:** Невалидированные пользовательские сообщения изолируются маркерами `<<<CUSTOMER_INPUT_START>>>` и не могут изменить системный промпт нейросети.
4. **Отказоустойчивость и безопасность данных:** Все операции резервирования запасных частей и создания заявок выполняются в транзакциях с блокировками строк (`SELECT ... FOR UPDATE`) и частичными уникальными индексами СУБД.

## 2. Матрица устранённых уязвимостей аудита

| Код | Уязвимость | Статус до аудита | Реализованное исправление |
|---|---|---|---|
| **K1** | Неавторизованный доступ через fallback | Без токена возвращался первый диспетчер | Удалён fallback. Любой запрос без валидного токена возвращает строгий HTTP 401. Внедрены зависимости `require_roles`. |
| **K2** | Несанкционированная смена пользователя `switch-user` | Любой мог получить токен произвольного пользователя | Доступно строго при флаге `DEMO_MODE=true`. При выключении флага эндпоинты возвращают 404. |
| **K3** | Несанкционированный сброс БД и загрузка Excel | Любой мог стереть базу или подменить данные | Доступно только авторизованному диспетчеру при `DEMO_MODE=true`. Проверка расширения `.xlsx`, размера (до 10 МБ) и безопасное имя файла. |
| **K4** | Эскалация привилегий при регистрации | Клиент мог сам назначить себе роль диспетчера или старшего инженера | Регистрация игнорирует роли и всегда создаёт пользователя с ролью `company`. Старшинство и квалификацию назначает только диспетчер. |
| **K5** | Открытые эндпоинты API | Эндпоинты `/ai`, `/orders`, `/equipment`, `/parts` были открыты | Все эндпоинты закрыты ролевой авторизацией `require_roles`. |
| **K6** | IDOR в обращениях клиентов | Компания могла читать чужие ветки диалогов | Введена фильтрация по `company_id` и `owner_user_id`. Чужие ветки возвращают 403 Forbidden. |
| **K7** | Двойная отправка инженера | Несколько диспетчеров могли отправить инженеров на одну поломку | Добавлен частичный уникальный индекс СУБД `uq_orders_active_thread` и атомарная блокировка `SELECT FOR UPDATE`. Повторная попытка возвращает 409 Conflict. |
| **B1** | Небезопасные коды верификации | `random.randint`, открытый текст в БД, нет лимита попыток | Генерация через криптостойкий модуль `secrets`, хранение SHA-256 хеша, лимит 5 попыток ввода, тайм-аут 60 секунд. |
| **B2** | Отсутствие ограничения частоты (Brute-Force & DoS) | Нет лимитов на вход, ИИ и генерацию кодов | Внедрён Rate Limiter: защита от подбора паролей, лимит ИИ (20 запросов в минуту), защита от спама аудитории. |
| **B3** | JWT секрет по умолчанию и TTL 7 дней | Секрет захардкожен, токен жил слишком долго | Запрет запуска в продакшене со стандартным ключом, сокращение TTL токена до 8 часов, отзыв сессий через `token_version`. CORS без `*` при `credentials=True`. |
| **B4** | Хранимый XSS через загрузку SVG-аватара | Разрешались любые файлы и `.svg` | Проверка реального содержимого через Pillow, строгий whitelist форматов (JPEG, PNG, WebP), запрет SVG, лимит 2 МБ и 2000x2000 px. |
| **B5** | Отсутствие заголовков безопасности | Нет CSP, clickjacking-защиты | Middleware внедряет CSP, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`. Документация `/docs` скрыта в продакшене. |
| **B6** | Утечка настроек в ошибках | Ошибки SMTP светили внутренние логины и пароли | Ошибки SMTP скрыты за общим текстом. Глобальный обработчик ошибок возвращает только анонимный `request_id`. |
| **B8** | Валидация входных данных | Тексты не ограничены, количество деталей не проверялось | Валидация через схемы Pydantic (максимальная длина текста, диапазон деталей от 1 до 10, проверка соответствия инженера городу и допуску). |
| **B9** | Prompt Injection к Gemini | Промпт склеивался из сырого текста клиента | Пользовательский текст экранируется маркерами `<<<CUSTOMER_INPUT_START>>>`. Ответ валидируется строгой схемой Pydantic. |
| **B10**| Отсутствие журнала аудита безопасности | Не велась фиксация критических действий | Таблица `audit_log` фиксирует входы, регистрацию, смену ролей, назначение инженеров и сброс данных. |

## 3. Криптографические стандарты

- **Хеширование паролей:** Алгоритм `bcrypt` с динамической солью (модуль `bcrypt >= 4.2.0`).
- **Генерация токенов и секретов:** Модуль `secrets` стандартной библиотеки Python (криптографически стойкий генератор псевдослучайных чисел ОС `os.urandom`).
- **Одноразовые проверочные коды:** Хеширование с использованием `SHA-256` (`hashlib.sha256`), проверка хеша в базе без сохранения открытого текста.
- **Подпись токенов:** JWT `HS256` с проверкой времени жизни (`exp`), идентификатора субъекта (`sub`), роли (`role`) и версии токена (`v`).
