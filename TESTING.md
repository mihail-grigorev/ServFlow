# Регламент тестирования платформы «КофеСервис Регион / ServFlow»

> **Документ описывает структуру, сценарии, методику и результаты всех видов автоматизированного и интеграционного тестирования платформы ServFlow (кейс 06, Navicon AI Fest 2026).**

---

## 1. Общая структура тестового контура

Тестирование платформы разделено на два независимых и взаимодополняющих уровня:

1. **Модульные и компонентные тесты (Pytest на SQLite In-Memory):**
   - **30 автоматических тестов**, изолированных от внешних сервисов.
   - Используют легковесную базу данных SQLite в оперативной памяти (`sqlite:///:memory:`) с пулом `StaticPool`.
   - Время полного прогона: **~35–45 секунд**.
   - Не требуют предварительно запущенного сервера или подключения к интернету.

2. **Интеграционные сквозные тесты (End-to-End Suite `test_suite.py`):**
   - **12 сценариев**, выполняемых по реальному HTTP-протоколу к запущенному экземпляру FastAPI.
   - Работают с боевой базой данных PostgreSQL (или файловой SQLite).
   - Проверяют реальные сквозные цепочки: логин диспетчера → выбор техники → ИИ-анализ ветки → бронь деталей → создание заказа → смена статуса инженером → отправка отчёта → раздача статики.

3. **Статический анализ и сборка (TypeScript & Vite):**
   - `tsc -b` — проверка строгой типизации TypeScript (0 ошибок).
   - `vite build` — валидация сборки фронтенда для продакшена.

## 2. Модульные тесты Pytest (`tests/`)

### 2.1. `tests/test_baseline.py` (7 тестов) — Базовая страховка функционала
Гарантирует, что исходная бизнес-логика и эталонные данные кейса остаются неизменными при любых доработках:

- `test_health`: проверка эндпоинта `/api/health`, статуса сервиса и соответствия опорной даты регламента (`16.11.2026 11:30`).
- `test_equipment_count_and_schema_snapshot`: проверка наличия ровно **12 кофемашин** в реестре оборудования, проверка схемы JSON (`code`, `client_name`, `address`, `city`, `model`, `serial_number`, `installation_date`).
- `test_spare_parts_count_and_schema_snapshot`: проверка наличия ровно **10 наименований запасных частей**, проверка складских остатков Москвы и Тулы, проверка совместимости деталей.
- `test_threads_count_and_schema_snapshot`: проверка группировки **23 обращений в 13 веток**, проверка наличия сообщений и корректности статусов.
- `test_warranty_rule_p9_for_pirs`: проверка правила **П-9** на кофемашине `EQ12` (Ресторан «Пирс», ввод 03.11.2026, 13 дней до опорной даты) — автоматическое признание случая гарантийным с бесплатным выездом.
- `test_order_lifecycle_and_schema_snapshot`: полный жизненный цикл заказа: создание заявки диспетчером → бронирование детали со склада (`V010`) → смена статуса на «В пути» → заполнение отчёта об осмотре и перевод в статус «Выполнен» → обновление даты последнего визита оборудования.
- `test_unregistered_equipment_rule_p2`: проверка правила **П-2** на симуляторе обращений: клиент Кафе «Ромашка» (кофемашина C200 №230) корректно распознаётся как незарегистрированный в договорах, заказ помечается для отдела продаж, а детали не бронируются.

### 2.2. `tests/test_security.py` (6 тестов) — Аудит безопасности (K1–K6)
Проверяет устранение всех критических уязвимостей, найденных в ходе аудита:

- `test_unauthenticated_requests_return_401`: проверка устранения уязвимости **K1**. Запросы без Bearer-токена к закрытым эндпоинтам (`/orders`, `/ai/analyze-thread/1`, `/equipment`, `/parts`) строго возвращают `401 Unauthorized`, а не права первого диспетчера.
- `test_demo_users_and_switch_user_locked_in_production`: проверка уязвимости **K2**. Эндпоинты `switch-user` и `demo-users` отключены (возвращают 404), если `DEMO_MODE=False`.
- `test_seed_reset_and_upload_excel_require_dispatcher`: проверка уязвимости **K3**. Сброс базы и загрузка Excel недоступны без токена диспетчера.
- `test_registration_ignores_role_elevation`: проверка уязвимости **K4**. При регистрации пользователя поля `role="dispatcher"` и `is_senior=True` отсекаются; создаётся только клиент с ролью `company`.
- `test_protected_endpoints_require_authorization`: проверка уязвимости **K5**. Эндпоинты `/api/orders/*`, `/api/equipment`, `/api/parts` закрыты от анонимного доступа.
- `test_company_idor_thread_isolation`: проверка уязвимости **K6**. Компания видит только свои ветки обращений и не может получить доступ к чужим веткам по прямому ID (`GET /api/threads/{id}` возвращает 403/404).

### 2.3. `tests/test_demo_qr.py` (8 тестов) — Демо-режим и QR-доступ зрителей
Проверяет функционал для защиты проекта перед жюри и залом:

- `test_demo_config`: получение публичной конфигурации демо-режима (`DEMO_MODE`, `PUBLIC_BASE_URL`).
- `test_demo_companies_auth`: ограничение доступа к списку QR-кодов компаний (только диспетчер).
- `test_qr_issue_all`: генерация криптографически стойких токенов и векторных QR-кодов (`segno`) для всех компаний.
- `test_qr_exchange_and_company_scope`: зритель обменивает токен по QR-коду на JWT-токен компании (TTL 2 часа) и получает доступ только к своей организации.
- `test_qr_exchange_invalid_token`: проверка отказа при невалидном токене (401).
- `test_qr_revoke_and_reissue`: отзыв всех активных QR-токенов в 1 клик и генерация новых ключей.
- `test_audience_anti_spam`: проверка ограничений зрительского ввода:
  - сообщение длиннее 1000 символов отклоняется (422/400);
  - лимит частоты: более 10 сообщений в минуту блокируется (429 Too Many Requests).
- `test_staff_pin_verification`: проверка ПИН-кода персонала (`2026`) для предотвращения случайного переключения ролей зрителями.

### 2.4. `tests/test_duplicate_dispatch.py` (4 теста) — Защита от двойной отправки инженера
Проверяет предотвращение повторных выездов и гонки резервирования деталей:

- `test_duplicate_order_sequential_rejection`: повторная отправка инженера на одну и ту же ветку отклоняется с HTTP `409 Conflict` и сообщением «По этому обращению уже сформирована заявка №...».
- `test_insufficient_stock_rejection`: попытка забронировать деталей больше, чем свободно на складе (`free < qty`), отклоняется с HTTP `409 Conflict`, а изменения откатываются (`rollback`).
- `test_order_creation_after_cancellation`: если предыдущий заказ был отменён («Отменен»), диспетчер может законно пересоздать новую заявку по тому же обращению.
- `test_concurrent_order_dispatch`: параллельное выполнение двух одновременных запросов на создание заказа через `ThreadPoolExecutor`. Ровно **один** запрос завершается успешно (200 OK), а **второй** получает 409 Conflict. Запчасть резервируется строго **один раз** (+1).

### 2.5. `tests/test_analytics.py` (5 тестов) — Аналитический слой и ClickHouse
Проверяет сбор аналитических событий и устойчивость при отсутствии ClickHouse:

- `test_track_event_and_persistence`: безопасное логирование события `ai_analysis` в таблицу `events` с сохранением задержки (мс), флагов гарантии и списка сработавших правил.
- `test_analytics_endpoints_permissions`: доступ к аналитике строго ограничен: 401 для анонимов, 403 для инженеров и компаний, 200 только для диспетчера.
- `test_analytics_summary_data_structure`: валидация формата ответа `/api/analytics/summary` (пустые выезды, процент автоматизации, задержка p50/p95, распределение правил П-1...П-10, дефицит деталей).
- `test_analytics_timeseries_structure`: проверка 7-дневной динамики выездов и обращений в `/api/analytics/timeseries`.
- `test_clickhouse_fallback_and_sync_graceful`: если ClickHouse недоступен или отключен флагом, фоновый воркер и API работают прозрачно на базе PostgreSQL без ошибок и падений.

## 3. Сквозной интеграционный сценарий (`test_suite.py`, 12 шагов)

Выполняется командой:
```bash
python test_suite.py
```

Проверяет 12 ключевых шагов живой системы:
1. `GET /api/health` — проверка работоспособности сервиса и опорной даты.
2. `POST /api/auth/login` — авторизация диспетчера (`dispatcher@kofeservice.ru`).
3. `GET /api/equipment` — получение и сверка 12 единиц техники.
4. `GET /api/parts` — получение и сверка 10 позиций запчастей.
5. `GET /api/threads` — проверка 13 веток входящих обращений.
6. `POST /api/ai/analyze-thread/10` — ИИ-диагностика ветки 10 (подтверждение гарантии П-9 и ремкомплекта).
7. `POST /api/orders` — создание сервисного заказа с бронированием деталей.
8. `PATCH /api/orders/{id}/status` — обновление статуса заявки («В пути»).
9. `POST /api/orders/{id}/report` — сдача отчёта инженера об осмотре и завершение заявки.
10. `POST /api/threads/simulate` — симуляция обращения по правилу П-2 (незарегистрированная машина).
11. `GET /` — проверка отдачи фронтенда `index.html`.
12. `GET /logo.png` — проверка отдачи логотипа компании.

**Результат:** `ALL 12 INTEGRATION TESTS PASSED WITH 100% SUCCESS!`

## 4. Инструкция по запуску тестирования

```bash
# 1. Запуск всех 30 тестов pytest:
python -m pytest tests/ -v

# 2. Запуск отдельного тестового модуля:
python -m pytest tests/test_duplicate_dispatch.py -v
python -m pytest tests/test_security.py -v

# 3. Запуск сквозного E2E тестирования (сервер должен быть запущен на порту 8000):
python test_suite.py

# 4. Проверка сборки фронтенда:
npm --prefix frontend run build
```
